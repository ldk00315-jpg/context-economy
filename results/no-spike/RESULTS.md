# 個別タスクの大幅増加を防ぐ変更 — 2026-09-08

## 結論

Routerから部分抜粋を選択する経路を撤去した。平均再取得確率が低くても、再取得した1件が高くつく問題は解消しないため、確率は許可の根拠にしない。明示的な範囲の全件検索・集計・項目取得と、完全圧縮の節約は残す。

前回84.5%増になった実測の4資料をローカルで再投入し、再取得確率0という楽観設定でもすべて原文を選ぶことを確認した。合計payloadは原文4,066→選択後4,066。参照先・公開禁止・後半のWARNを最初から含む。追加Astra呼び出しは0。これは決定論的な再生で、新しいモデル品質・総usageの実測ではない。

## 境界ごとの対策

| 境界 | 動作 |
|---|---|
| 不完全な資料の選択 | Routerでは許可しない。確率0でも完全情報へ戻る |
| 最終入力の組立 | 説明・質問・エスケープ込みの候補と原文を再計数。候補が大きければ原文 |
| 入力上限不明・予算不足 | 送信前に拒否。欠落させて通さない |
| 出力・推論の増加 | 接続先で強制する出力上限を予算に予約する契約 |
| 二重実行・同時実行 | SQLiteの論理request ID一意制約で一度だけ許可 |
| 中断・タイムアウト・使用量不明 | 送信前の記録を残し、自動再試行・原文再送をしない |
| 台帳の保存失敗 | モデルを呼ぶ前に失敗させる |
| 使用量の超過・複数呼出しの申告 | アダプター契約違反として記録、再試行なし |

Gateには外部通知や自動継続機能はない。戻り値・例外・statusを呼出し側へ返す。pendingやfailed_or_unknownを成功と扱わない。同じ論理仕事には同じID、同じ永続台帳を使う。台帳削除や別IDへの付け替えによる再試行は、この保護を回避するため禁止。

## 上限の意味と接続制約

plan_callの比較対象は「原文入力の上限＋同じ最大出力」。実際の原文回答がたまたま短かった場合より、最適化回答が長くなる可能性までは消せない。原文の実使用量に対する無条件の削減保証ではない。

count_input_upper_boundには接続先の実トークナイザーと隠れた指示等を含む確実な上限が必要。未知ならNoneで拒否する。sendは、物理呼出し1回、SDK retryとツール無効、推論込み出力上限の強制を満たす信頼されたアダプターを接続する。これらをライブラリが外部SDK内部へ強制する機能はない。アダプターが契約に反して超過した場合、usageで検出しても過去の消費は戻らない。

従来のAstra CLI実験は最終入力・出力の確実な上限強制を確認しておらず、SingleCallGateには未接続。今回は追加の有料/サブスク推論を使って安全性を検証したとは主張しない。低水準focus/readは実験用として残り、直接使えばRouterの保護対象外。通常経路に自動取得ループを戻さないことが必要。
